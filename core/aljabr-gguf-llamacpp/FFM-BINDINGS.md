# llama.cpp FFM bindings

The Java FFM wrappers under `src/main/java/tech/kayys/aljabr/llama` were
generated by `jextract`. They are tied to the C declarations in the llama.cpp
headers and to the ABI exported by the runtime native libraries. Do not update
the headers independently of the native library version.

## Regenerate the header binding

Requirements:

- A JDK 22+ compatible `jextract` executable available on `PATH` (or pass
  `-PjextractExecutable=/absolute/path/to/jextract`).
- A llama.cpp source checkout whose `include/llama.h` matches the native
  llama.cpp libraries used at runtime.
- The matching ggml headers, normally at `../ggml/include` relative to the
  llama.cpp `include` directory.

Run from the Aljabr repository root:

```sh
./gradlew :core:aljabr-gguf-llamacpp:generateLlamaFfmBindings \
  -PllamaCppInclude=/path/to/llama.cpp/include
```

If ggml headers are stored elsewhere, add
`-PggmlInclude=/path/to/ggml/include`. The same settings can be provided using
`LLAMA_CPP_INCLUDE`, `GGML_INCLUDE`, and `JEXTRACT` environment variables.

The task writes jextract output under the module's `build/` directory and
copies only `llama_h.java` into the checked-in source package. The other
checked-in wrapper classes depend on that header class, so regenerate against
the matching header revision and review the diff before committing. The task
does not fetch llama.cpp, download native binaries, or run native inference.

## Compatibility checks before committing

1. Record the exact llama.cpp commit used to generate the binding.
2. Confirm the checked-in generated struct/callback wrappers still match the
   declarations in that checkout; regenerate the full wrapper set if they do not.
3. Run `./gradlew :core:aljabr-gguf-llamacpp:compileJava` with Java 25.
4. Run the relevant native smoke test only on a machine with matching llama.cpp
   libraries installed.

A successful jextract run alone does not prove native ABI compatibility.
